## §0 源算子解读与迁移分析

### §0.1 第一问:语义(What —— 必须保持)

| 要素 | 解读 | 依据 |
|---|---|---|
| 数学语义 | 沿最后一维取 **top-k**(按值排序取前 k),输出**索引** | GPU 实现为 radix-select;`out_dtype = int32` |
| I/O 契约 | 输入 fp32;输出 int32 索引;`k = topk` | GPU manifest workloads:`{'batch':1,'seq_len':32768,'seq_len_kv':65536,'kv_group':1,'topk':1024,'in_dtype':'float32','out_dtype':'int32'}`(另有 topk=2048 一条) |
| **关键语义:输出顺序无关** | **top-k 结果的顺序不影响正确性** —— 测试用**集合比较**(`_set_compare`),而非逐元素比对 | 旧设计 §2.2;**该自由度是本设计能大幅简化的前提** |
| 并列(ties)语义 | 值相等时的取舍**不由顺序定义**(集合比较口径) | 同上 |
| 形状约束 | GPU 侧依赖 `T.dynamic()`;`seq_len=32768`、`seq_len_kv=65536` 属**大规模** | workloads |

**完成标准核对**:可写出与源算子**集合等价**的 golden(顺序无关)。

### §0.2 I/O 契约(显式)

| 项 | 值 |
|---|---|
| 输入 | `(batch, seq_len, ...)` 形状的 fp32 张量 |
| 输出 | **int32 索引**,每行取 `k = topk` 个 |
| 归约轴 | **最后一维**(`seq_len_kv` 方向) |
| 动态轴 | GPU 侧用 `T.dynamic()`;npuir **要求静态形状** ⇒ 必须构造期固定(K1/K3 的含义) |
| **顺序** | **无序**(集合等价) |

### §0.3 第二问:实现算法(How)

**GPU 侧算法(必须被替代)**:CUDA-thread **radix-select** ——
`threads=1024` 线程协作;`T.get_thread_binding()` 取线程号;**共享 256-bin 直方图** 配合 `T.atomic_add(..., return_prev=True)` 做计数;`T.sync_threads()` 做块内屏障;按 radix 逐轮收敛到第 k 大的阈值。

**npuir 侧缺失的机制(逐条)**:

| GPU 机制 | npuir 是否可用 | 依据 |
|---|---|---|
| `threads=1024` / 线程号 | ❌ **不存在** | K3/K9:去掉 `threads`,并行度由 `block_*` / 核数表达 |
| 块内 `T.atomic_add(..., return_prev=True)` | ❌ **无块内原子** | 实测 |
| `T.sync_threads()` 屏障 | ❌ **无 CUDA 语义屏障** | 实测;npui 的同步由编译器按依赖插入 |
| `T.dynamic()` 形状 | ❌ **形状必须静态** | 实测 |
| 共享 256-bin 直方图 | ❌ 依赖上述原子 | — |

⇒ **GPU 的 radix-select 在 npuir 上无法逐句移植**,必须换算法骨架。

### §0.4 第三问:优化手段(Why fast)

GPU 侧的手段(radix 分轮收敛、块内并行计数、屏障同步)全部**绑定在线程模型上**,故**迁移后无一可直接保留**;能保留的只有**意图**:

| 意图 | 是否可承接 | 承接方式 |
|---|---|---|
| 单遍扫描(避免多轮 GM 往返) | ✅ **意图可保留** | 方案一:候选缓冲流式 top-k(目标 1 次 GM 遍历) |
| 用"桶/阈值"缩小候选 | ✅ 意图可保留 | 重设计为**阈值 + 压缩**,而非直方图 |
| 块内并行计数 | ❌ **不可承接** | npuir 无块内原子;改为 `vcmp`+`cumsum` 求前缀和 |
| 屏障同步 | ❌ 不可承接 | 由编译器自动同步 |

|---|---|---|

### §0.6 NPU 算法重设计

> **本节是既有 `tileops/kernels/attention_indexing/topk_selector/DESIGN.md`(421 行)的浓缩**;
> 原始文档包含**完整的探针矩阵与反例**,本设计沿用之并**不重复列出**。证据位置见下。

#### 重设计项 0 —— **原语基线(全部经实测,含反例)**

**可用 ✅**(依据:既有设计 §3.1/§3.4 的实测):

| 原语 | 备注 |
|---|---|
| `vcmp(A, B, C, mode)` | **掩码缓冲必须是 uint8** |
| `vselect(Cond, A, B, Out)` | — |
| `cumsum(src, dst, dim, reverse)` | 导出名为裸 `cumsum`,**无** `vcumsum` 别名;**拒 uint8 操作数** |
| **发散散射写** `out[dst[i]] = i` | 带 guard 与不带 guard **均可用** |
| **完整压缩链** `vcmp → vselect → cumsum → scatter` | **端到端已验证** |

**不可用 / 有坑 ❌**:

| 项 | 现象 |
|---|---|
| `vcast(uint8 → int32)` | **codegen 卡死**(~140% CPU 持续 10+ 分钟) |
| uint8 缓冲的 **UB→GM 拷贝** | **返回原始输入**而非掩码 |
| uint8 的**逐元素读**用于 guard | **结果错误** |
| 1-D 缓冲的 `reduce_sum`(**int32**) | **恒返回 0** |
| 1-D 缓冲的 `reduce_sum`(**fp32**) | **段错误** |
| 2-D 的 GM→UB `T.copy` | **实测拷贝结果全为 0** |
| 48 轮展开 | `bishengir-compile` **ABORT**(`ERR99999`) |
| 4 轮 × `T.serial(12)` | **段错误(core dumped)** |
| in-place `vselect`(Out ∪ A 别名) | **段错误** |

**归纳出的核心规则(本设计的地基)**:

> **uint8 缓冲只在"作为 `vcmp` 结果被 `vselect` 立即消费"时安全**;任何其它用法(转 int32、拷回 GM、逐元素读)均坏。

#### 重设计项 1 —— 总体思路:**阈值 + 压缩**,而非直方图

用"阈值 + 压缩"替代 GPU 的直方图计数:先判定一个阈值 $T$ 使满足 $x \ge T$ 的元素个数 $\approx k$,再用已验证的压缩链把候选**紧凑地**收集成前缀。**计数**由 `cumsum` 提供(避开无块内原子的缺口)。

#### 重设计项 2 —— 单调键:把浮点比较换成整数比较

为让"阈值 + 大小比较"可落在整数域(便于 `vcmp`/`cumsum`),把 fp32 值映射为**保序的整数键**。该变换的目的是**让比较与计数在同一整数域上完成**。

#### 重设计项 3 —— 两条实现候选

| 方案 | 形式 | 目标 | 状态 |
|---|---|---|---|
| **方案一(优先)** | **候选缓冲流式 top-k** | **1 次 GM 遍历** | 未实现(卡在 §重设计项 4) |
| 方案二(兜底) | **位级二分 + 一次压缩** | 多轮但结构更简单 | 未实现 |

#### 重设计项 4 —— **阻塞点:循环结构(BishengIR 编译器)**

**★ 本条已由 `repro/TRAP-blocker-loop-structure.py` **重新实测**,并修正了两处措辞(见下)。**

**实测矩阵(910B2C / CANN 9.0.0 / wheel `0.1.2+npuir+7fc4a3c8`)**

| 循环体 | W1:静态展开 48 轮 | W2:`T.serial(4) × T.serial(12)` |
|---|---|---|
| **弱体**(单条 `vcmp`) | ✅ **编过并运行** | ✅ **编过并运行** |
| **忠实体**(完整压缩链:`vcmp → cumsum → vselect → scatter` + 阈值更新) | ⛔ **`DiagnosticError`** | ⛔ **`DiagnosticError`** |

⇒ **结论:阻塞成立,但它依赖循环体** ——

1. **只有循环内装的是"真实收敛工作"(压缩链)时才爆**;把循环体换成单条 `vcmp` 就编得过。**这一点是本设计必须记下的关键事实**:它说明阻塞**不是**"循环语法"本身,而是"**循环 × 压缩链**"的组合。
2. **当前可复现的症状是编译期 `DiagnosticError`**("one or more error diagnostics were emitted, please check diagnostic render for output"),**而非**早先会话记录的 `bishengir-compile` **ABORT(`ERR99999`)** 与 **core dump**。三种症状同属"编译期失败",但**只有 `DiagnosticError` 是本轮亲自复现的**;另两种为**前序记录,未在本轮复现** —— 如实并列,不互相冒充。
3. **首次 repro 曾用弱体,结果"未复现"** —— 该失败已当场纠正(把体换成忠实体),并把弱体保留为**对照**(`--body trivial`),使"体强弱决定是否爆"这一事实**可被独立验证**。

**证据**:`examples/topk_selector/_topk_selector_kernel/repro/TRAP-blocker-loop-structure.py`(自包含,`--wall w1|w2 --body full|trivial`,`--body full` 为默认)

#### 重设计项 5 —— ~~「可用部件互相补不上」~~ **【已推翻,2026-10-16 重测】**

> **本节原结论已作废。** 原设计依据早期探针断言"计数可用的形态拷贝不可用、拷贝可用的形态计数不可用",据此判该算子整体不可实现。
> **重测(`repro/PROBE-topk-primitive-baseline.py`)表明该矩阵三处判反**,现按实测更正如下。

**重测矩阵(910B2C / CANN 9.0.0 / wheel `0.1.2+npuir+7fc4a3c8`,每项均核对真实数值)**

| 形态 | **实测结果** | 原设计的说法 | 判定 |
|---|---|---|---|
| `copy1d`(1-D GM→UB→GM 往返) | ✅ **PASS**(数值吻合) | 可用 | 一致 |
| **`copy2d`**(2-D GM→UB→GM 往返) | ✅ **PASS**(数值吻合) | ❌ 称"实测全为 0" | **原说法有误** |
| `red1d_i32`(1-D int32 `reduce_sum`) | ⛔ **WRONG**(得 `5.74e-42`,应为 `4096`) | 称"恒返回 0" | 方向一致(确不可用) |
| **`red1d_f32`**(1-D fp32 `reduce_sum`) | ✅ **PASS** | ❌ 称"段错误" | **原说法有误** |
| `red2d_i32` / `red2d_f32` | ⛔ 编译期 `DiagnosticError` | ❌ 称"2-D 可算" | **原说法有误** |
| **`loopcount`**(`T.serial` 遍历 tile + **简循环体计数**) | ✅ **PASS**(计数与参考一致) | — | **重构形态可用** |
| **`compact`**(压缩链 `vcmp → vselect → cumsum`,**无循环**) | ✅ **USABLE** | 可用 | 一致 |

**更正后的结论**

1. **"1-D 拷贝正常但计数不可用"不成立** —— 1-D fp32 归约**实测可用**;真正不可用的是 **1-D int32** 归约。
2. **"2-D 计数可用但拷贝全 0"不成立** —— 2-D 拷贝**实测正确**,而 2-D 归约**反而编不过**。
3. ⇒ **两个"可用部件"从来不是互斥的**;原结论把"int32 归约不可用"误当成"1-D 计数不可用",把"2-D 归约的某种写法不可用"误当成"2-D 拷贝不可用"。
4. **真正可用的地基是**:**1-D 形态** + **fp32 域计数** + **`T.serial` 简循环体** + **环外压缩链**。
5. ⇒ **本算子的"互相补不上"阻塞解除**,重构路线(重设计项 3 的**方案一:候选缓冲流式 top-k**)具备了原语基础。

> ⚠️ **教训(与本文档的 `gqa_fwd` 姊妹条同因)**:**早期探针的结论不能直接当结论引用**。本迁移已两次遇到"旧探针结论与重测不符"(`gqa_fwd` 的"仓库零命中"、本节的三条矩阵),两次都靠**忠实重测**纠正。凡引用早期探针结论,须先重跑。**

**仍成立的约束**:`red1d_i32` 不可用(计数必须走 **fp32** 域,不能对 int32 掩码直接归约);`red2d_*` 编不过(2-D 归约的该写法不可用)。

## §1 概述

### §1.1 算子概述

`TopkSelectorOp` —— 沿最后一维取 top-k,输出 **int32 索引**。用于稀疏注意力(如 NSA/DSA 系的 token 选择)。
**NPU 侧目标算法**:阈值 + 压缩链(`vcmp`→`vselect`→`cumsum`→scatter),计数由 `cumsum` 承担。

### §1.2 计算语义

- 输入:fp32,归约轴为最后一维($N=$ `seq_len_kv`)
- 输出:每行 `topk` 个 **int32 索引**,**顺序无关**

### §1.3 算子特征分析

| 维度 | 判定 |
|---|---|
| 计算类型 | **纯 Vector + 前缀和 + 散射写**(无 Cube) |
| 复杂度级别 | **多阶段**(判定阈值 → 压缩 → 散射);**循环结构是必需项**(§0.6 重设计项 4) |
| 动态 shape | GPU 侧 **有**;npuir **必须静态** |
| **可行性** | **被编译器阻塞**(见 §0.6 重设计项 4/5) |

### §1.4 算法描述

见 §0.6 重设计项 1–3。**无已实现版本** —— 两条候选方案均未落地。

### §1.6 算法调研与优化分析

#### §1.6.0 算法调研(Phase R —— 完整调研)

| 问 | 结论 | 依据 |
|---|---|---|
| **R1 等价化简公式** | **无可比 GPU 更省的等价形式;但换算法族是必需的** | 候选:① **radix-select(源)** —— 依赖线程模型,**不可用**;② **阈值 + 压缩(采纳思路)** —— 用 `cumsum` 求前缀和替代块内原子计数;③ **完整排序后取前 k** —— 正确但 `O(N log N)`,且 npuir 无高效排序原语;④ **直方图分桶** —— 与 ② 同族,但桶计数仍需原子或多次归约,在 npuir 上更贵 |
| **R2 在线算法** | **有,且是设计目标** | **方案一"候选缓冲流式 top-k"以 1 次 GM 遍历为目标** —— 这是本算子在 npuir 上唯一现实的性能路线 |
| **R3 复杂度四口径** | **FLOPs / 扫描遍数 / 中间缓冲**由所选方案决定;**访存**至少 $M\cdot N\cdot\text{elem}$(读 1 遍)+ 输出 $M\cdot k\cdot 4$ | GPU manifest 的 roofline 由 `topk_selector_roofline` 函数给出(非四则表达式),**本设计沿用其结果而不重算** |
| **R4 硬件亲和** | **可用的向量原语很有限且有反例**:`vcmp`/`vselect`/`cumsum`/散射写/压缩链可用;`uint8` 除"立即被 `vselect` 消费"外**全坏**;1-D `reduce_sum` 在 int32/fp32 上分别"恒 0"/段错误;**多轮循环结构编不过** | §0.6 重设计项 0/4/5 的实测矩阵 |

**调研结论**:思路选定(**阈值 + 压缩**),但**实现路径被编译器阻塞**;**不是"未调研",而是"调研充分后仍不可实现"**。

**设计期 roofline 估算下界(D-2)**:因实现不存在,**不做**虚假估算。

#### §1.6.2 向量化替代分析

| # | 计算点 | 类型 | 判定 | 依据 / 理由 |
|---|---|---|---|---|
| V1 | 阈值判定 | 逐元素 | **已向量化替代** | `vcmp`(掩码必须 uint8) |
| V2 | 候选压缩 | 前缀和 + 选择 | **已向量化替代** | `cumsum` + `vselect`(**压缩链端到端已验证**) |
| V3 | 散射写索引 | 散射 | **已验证可用** | 发散散射写(带/不带 guard 均可) |
| **V4** | **多轮收敛循环** | **外层循环** | **无法替代 / 无法编译** | **W1 静态展开 48 轮 → ABORT;W2 `T.serial` 4×12 轮 → 段错误** —— 这是本算子**不可实现**的直接原因 |
| V5 | 计数 | 归约 | **形态受限** | 1-D:int32 恒 0 / fp32 段错误;2-D:可算但**该形态的 GM→UB 拷贝全 0** |

**结论**:逐元素与压缩热点(V1–V3)已向量化;但 **V4 的循环结构在两种自然写法下均编不过**,**V5 的两种形态互补性缺失** ⇒ **整体不可实现**。

#### §1.6.3 向量化轴与数据布局决策

- **候选轴**:① 沿行(每行独立 top-k);② 沿列(跨行共享计数)。
- **判据**:因 **2-D 形态的 GM→UB 拷贝实测全 0** ⇒ ② **不可用**;① 的**计数**在 1-D 形态上不可用(§0.6 重设计项 5)。
- **结论**:**两个候选轴都无法同时满足"拷贝正确"与"计数可用"** —— 该两难是 §0.6 重设计项 5 的实质。

### §3.2 API 映射表

| 计算逻辑 | TileLang-NPUIR API | 状态 / 佐证 |

| 阈值比较 | `T.vcmp(A, B, mask, "ge")` | ✅ 可用;**掩码必须 uint8** |
