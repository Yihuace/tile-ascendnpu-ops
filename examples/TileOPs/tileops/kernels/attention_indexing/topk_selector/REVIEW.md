## 检视详情

### 0. 源算子理解与迁移分析 — pass

**已亲自 Read 源码核对**:

| `§0` 断言 | 核对结果 |
|---|---|
| GPU 侧算法是 **CUDA-thread radix-select** | ✅ 抽取文件 `_topk_selector_kernels.py` 使用 `threads=1024`、`T.get_thread_binding()`、共享 256-bin 直方图 + `T.atomic_add(..., return_prev=True)`、`T.sync_threads()`、`T.dynamic()` |
| **npuir 缺全部四种机制** | ✅ 与既有设计的实测结论一致(去 threads / 无块内原子 / 无 CUDA 屏障 / 形状须静态) |
| **输出顺序无关(集合等价)** | ✅ 源仓测试用 `_set_compare`(集合比较),非逐元素比对 —— **该自由度是设计能简化的前提** |
| I/O 契约(fp32 → int32 索引,`k = topk`) | ✅ GPU manifest workloads 的 `in_dtype: float32` / `out_dtype: int32` |
| 大规模(`seq_len_kv = 65536`、`topk = 1024/2048`) | ✅ manifest workloads |
| roofline 由函数给出(`topk_selector_roofline`) | ✅ manifest 原文;**设计明确"沿用其结果而不重算"** —— 处置正确(不臆造公式) |

**核心判定的独立复核(本审阅重点)**

**① "这是算法层重设计,不是 API 替换"的判定**:本审阅确认 —— GPU 的 radix-select **每一轮都依赖块内并行计数与屏障**,而这两者在 npuir 上都不存在。**逐句移植不可能**。设计的 §0.5 把"radix 收敛骨架""块内直方图计数""动态形状"三项判为**重新设计**、把"线程屏障"判为**舍弃**,**判定正确**。

**② 原语基线(§0.6 重设计项 0)的可靠性**:基线由**实测矩阵**给出,其中**既有可用项(完整压缩链端到端验证)也有反例项(9 条不可用/有坑)**。本审阅确认:

- **可用项**中最关键的是 **`vcmp → vselect → cumsum → scatter` 压缩链端到端验证** —— 这是本设计能提出"阈值 + 压缩"思路的**唯一依据**;
- **反例项**中最有约束力的是 **`uint8` 只在"被 `vselect` 立即消费"时安全** —— 该规则**同时解释了**三条看似不相关的失败(`vcast(uint8→int32)` 卡死、uint8 UB→GM 拷贝返回原值、uint8 逐元素读结果错);
- 该基线的**完整矩阵与复现记录**在原始设计 `tileops/kernels/attention_indexing/topk_selector/DESIGN.md` §3.1/§3.4,本设计**引用而不重复** —— 处置得当(避免双份矩阵发散)。

**③ 阻塞点定位的准确性**:设计把阻塞点定位在 **BishengIR 编译器的循环结构**上(重设计项 4 的 W1/W2),并**明确区分**于"算法不可行":

| 区分 | 依据 |
|---|---|
| **不是**"算法不可行" | 压缩链端到端可用(V1–V3 均有可用原语);两条候选方案在算法层成立 |
| **是**"编译器不支持其必需结构" | W1 静态展开 → `bishengir-compile` ABORT(`ERR99999`);W2 `T.serial` → 段错误 |

本审阅确认:**该定位正确且重要** —— 它决定了后续的解锁路径是"等编译器支持/换工具链版本",**而不是**"再想一个算法"。

**④ 第二道墙(重设计项 5)的实质**:设计用一张 2×2 表把"1-D 拷贝正常但计数不可用 / 2-D 计数可用但拷贝全 0"并置,得出"两个候选轴都无法同时满足"的结论。本审阅确认该并置**成立**,且 §1.6.3 把它作为轴选择的判据 —— **逻辑闭合**。
