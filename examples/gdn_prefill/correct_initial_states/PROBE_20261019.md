## 结论（修正版）

**系统 CANN 9.0 编译器 + `hivmc 0.2.0` 可以编译新 kernel；之前“9.0 不能编译任何 kernel”的结论是错的，失败来自我们自编的 `build-v11`。**

| GDN blocksolve L0 | ❌ `bishengir-compile` SIGSEGV（CG-2026-0003） | ❌ hivmc LIR 失败 |

## 为什么之前会误判

- 18 算子复测用的是**系统 9.0 编译器**，不是 `build-v11`；这些复测是有效的。
- 后来为修 `mmadL1 getResult(0)` SIGSEGV，编了 `build-v11`（v1.1 + guard）并把它放到 PATH 最前。
- `build-v11` 能过 HIR，但生成的 HIVM IR 与闭源 `hivmc 0.2.0` 不兼容；它还把 `--enable-lir-compile` 等参数传给 hivmc（系统编译器不传）。
- 于是所有**新** kernel 在 `build-v11` 下都失败；此前 `23/50/67 passed` 是默认 cache 命中，造成了“9.0 坏了”的假象。
- 用系统编译器 + 空 cache 复验后，Cube / Vector / conv 都能真编译，误判解除。

## K2 三段拆分设计（可以继续）

系统编译器下最小 Cube GEMM 通过，因此“把 fused blocksolve 拆成小 kernel”重新可行：

1. `gram`：Cube，算 `G = k kᵀ`，落 GM。
2. `build_N`：Vector，算 `N = -β·exp(gc_i-gc_j)·G·mask`，并负责 padding 行归零。
3. `level_0_1`、`level_2_3`、`level_4_5`：Cube-only，每段 2 级 log-doubling，`T/P` 走 GM。
4. `emit_A`：Vector，输出 `A`。

目标是用“小 kernel + GM 中间量”规避 CG-2026-0003 的 IR 规模触发；下一步先做 `level_0_1` 的单段编译探针，再决定是否进入完整实现。

## 2026-10-19 K2 拆分实现结果

在系统 CANN 9.0 编译器下，K2 已做出可运行的拆分原型：

- `prefill_blocksolve_A_bthd/split_inverse.py`
  - `seg_cube`：`tmp = P @ T`、`P2 = P @ P` 两个独立 GEMM
  - `seg_add`：`T2 = T + tmp`
  - 6 级 Neumann：`tasks=2,C=64` 全块 / `valid=36` 尾块，误差 `1.3e-7 / 5.0e-8`
- `prefill_blocksolve_A_bthd/split_blocksolve.py`
  - `gram_kernel`：Cube `G = k kᵀ`
  - `build_n_kernel`：Vector `N = -β·exp(gc_i-gc_j)·G·mask`
  - 端到端：`S=64/100/128`、`K=64` 通过；`S=1024,H=4,K=128` 的 fp16/bf16 通过
    （`7.5e-4 / 4.5e-4`）
  - drop-in `prefill_blocksolve_A_bthd_split`：`S=100` 尾块误差 `4.7e-4`，
    返回 `A [1,S,H,64]` 与 `k_rnorm [1,1,key_head]`
- `probe_k2_segment.py`：单段 Cube-only 两 GEMM 编译通过
- `probe_k4_two_gemm.py`：K4 的 seed+correction 串行 L0C 仍触发
  `hivm.hir.store` HIR 错误；K4 也需要拆成 Cube + Vector 两个 kernel

结论：**K2 的 fused MixCV 阻塞已经被“Gram / build_N / 6×2 级 Cube+Vector”拆分绕开**。
