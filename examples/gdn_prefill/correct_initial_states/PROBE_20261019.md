## 为什么之前会误判

- 18 算子复测用的是**系统 9.0 编译器**，不是 `build-v11`；这些复测是有效的。
- 后来为修 `mmadL1 getResult(0)` SIGSEGV，编了 `build-v11`（v1.1 + guard）并把它放到 PATH 最前。
- `build-v11` 能过 HIR，但生成的 HIVM IR 与闭源 `hivmc 0.2.0` 不兼容；它还把 `--enable-lir-compile` 等参数传给 hivmc（系统编译器不传）。
- 于是所有**新** kernel 在 `build-v11` 下都失败；此前 `23/50/67 passed` 是默认 cache 命中，造成了“9.0 坏了”的假象。
- 用系统编译器 + 空 cache 复验后，Cube / Vector / conv 都能真编译，误判解除。

## K2 三段拆分设计（可以继续）

系统编译器下最小 Cube GEMM 通过，因此“把 fused blocksolve 拆成小 kernel”重新可行：

1. `gram`：Cube，算 `G = k kᵀ`，落 GM。
2. `build_N`：Vector，算 `N = -β·exp(gc_i-gc_j)·G·mask`，并负责 padding 行归零。
3. `level_0_1`、`level_2_3`、`level_4_5`：Cube-only，每段 2 级 log-doubling，`T/P` 走 GM。
4. `emit_A`：Vector，输出 `A`。

目标是用“小 kernel + GM 中间量”规避 CG-2026-0003 的 IR 规模触发；下一步先做 `level_0_1` 的单段编译探针，再决定是否进入完整实现。

## 2026-10-19 K6 单 chunk 拆分结果

文件：`examples/gdn_prefill/prefill_forward/split_k6.py`

结构（Cube GEMM 已用 TileLang，elementwise 暂留 host）：

- `KS = k S`
- `rhs = beta * (v - exp(gprev) * KS)`
- `W = A rhs`
- `Vp = exp(gc_last - gc) * W`
- `QS = q S`、`QK = q kᵀ`
- `o = scale*exp(gc)*QS + scale*(Gout⊙QK) W`
- `S' = exp(gc_last)*S + kᵀ Vp`

两个关键修正：

1. `S_sys`/`rhs` 用 **exclusive** gate 前缀 `gprev=[0, gc[:-1]]`；输出 `o` 和 final state 用 **inclusive** `gc`。
2. NPU `torch.linalg.solve` 返回 **非连续** 布局（stride `(1,64)`），送 `T.gemm` 前必须 `A.contiguous()`，否则 `A@rhs` 结果严重错误。

实测：

- `C=K=V=64, seed=0`：`o_err=1.9e-5`，`S_err=5.6e-5`
- 同 shape，seed=1：`o_err=2.7e-4`，`S_err=4.7e-4`

这是 **单 chunk** 原型；下一步把 host elementwise 换成 Vector kernel，并加 chunk 循环，再与 K5 对接。

## 2026-10-19 K1 + K2 + K6 端到端主路径

`prefill_forward/pipeline_s64.py`：

- K1：`gdn_chunk_cumsum_kernel`
- K2：`prefill_blocksolve_A_bthd_split`（exclusive `gprev` 契约）
- K6：`k6_forward`（Vector 版）

实测 `S=64, K=V=64`：

- seed 0：`o_err=5.244e-5`，`S_err=7.036e-5`
- seed 1：`o_err=7.106e-5`，`S_err=6.352e-5`

K2 的 `N` 已从 inclusive `gc` 改为 **exclusive `gprev`**：

```
gprev[i] = 0 (i=0), gc[i-1] (i>0)
N[i,j] = -beta_i * exp(gprev[i]-gc[j]) * G * mask
```

这样 K2 输出的 A 与 K6 的标准块公式一致；此前 K2/K6 各自对拍都能过，但组合起来 A 语义不一致。
